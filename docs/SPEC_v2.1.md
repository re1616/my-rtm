## 2. Нормативные требования по итогам ревизии

Эти требования обязательны для сервера и обоих клиентов; каждое закреплено автотестом, и регресс блокирует слияние в `main`.

### 2.1. Конфигурация

- **CFG-1\*must.** Значения из переменных окружения всегда перекрывают значения по умолчанию в `application.conf`.
- **CFG-2\*must.** Вне `TASKLY_ENV=dev` сервер не стартует, если `JWT_SECRET` отсутствует, короче 32 байт или совпадает с dev-значением. То же для ключей Stripe, FCM и VAPID.
- **CFG-3\*must.** Интеграционные и E2E-тесты отказываются запускаться против БД, имя которой не оканчивается на `_test`.
- **CFG-4\*must.** Клиенты не содержат секретов: адрес API, ключ VAPID (публичный) и DSN Sentry задаются на этапе сборки для каждого окружения.

### 2.2. Безопасность данных

- **SEC-1\*must.** Владелец сущности назначается только при первом создании; `create` с существующим чужим id отклоняется (`409 conflict`), владелец не меняется ни одной операцией, кроме явной передачи.
- **SEC-2\*must.** Ссылки (`list_id`, `parent_id`, `location_id`, теги) проверяются на принадлежность тому же scope; ссылка на чужую сущность → `403`.
- **SEC-3\*must.** Scope каждой операции, запроса `/v1/sync/changes` и подписки WebSocket вычисляет сервер по сущности и членству в списках; значение от клиента используется только как подсказка и сверяется.
- **SEC-4\*must.** Матрица доступа (владелец / участник с правом edit / участник view / посторонний) × (каждый маршрут и тип операции) покрыта автотестами.
- **SEC-5\*must.** Сессии: access-токен 15 мин, refresh-токен с ротацией и обнаружением повторного использования (повтор → отзыв всей цепочки).
- **SEC-6\*must.** Rate limiting на всех маршрутах: 429 + `Retry-After`; `/v1/auth/*` — 10 попыток в минуту на IP и 5 неудачных на аккаунт до CAPTCHA.
- **SEC-7\*must.** Эндпоинт `/v1/features` для удалённых фича-флагов: по пользователю, тарифу и версии клиента, кэш 5 мин, rollout по проценту, аварийное отключение одной нотой. Флаги используются в клиентах и в бэкенд-сервисах.

### 2.3. Синхронизация

- **SYNC-1\*must.** Каждая операция пакета выполняется в отдельном savepoint; ответ содержит результат по каждой (`ok` / `rejected` с кодом / `conflict_resolved`).
- **SYNC-2\*must.** Идемпотентность по ключу `(user_id, op_id)`; повтор возвращает сохранённый результат.
- **SYNC-3\*must.** Слияние полей — только через общий `MergeEngine`; серверная и клиентская реализации не дублируются.
- **SYNC-4\*must.** Завершение повторяющейся задачи вызывает общий `Recurrence` в той же транзакции, пишет `change_log` и создаёт ровно один следующий экземпляр. Поддерживаются every/after, BYDAY, UNTIL, **COUNT** (корпус тестов расширяется ~20 кейсами). **DST-политика:** несуществующее локальное время (переход на «весну») сдвигается вперёд; неоднозначное время (осень) — берётся первое вхождение. Повторы с временем идут по локальному времени пользователя, не по UTC.
- **SYNC-5\*must.** Фильтр `?q=`, умные списки на сервере и в iCal-фиде — только через общий `QueryParser` → `SqlBuilder`.
- **SYNC-6\*must.** Клиент синхронизирует все сущности своих scope, включая списки, теги, локации и членство в общих списках, созданные на других устройствах.
- **SYNC-7\*must.** Версия протокола передаётся в заголовке `Taskly-Sync-Version`; сервер поддерживает текущую и предыдущую мажорную версию, на более старую отвечает `426` с инструкцией обновиться.

- **WEB-S2\*must.** Отправка по порядку, удаление только после ack (сделано); экспоненциальная задержка 1 с → 5 мин с джиттером; операции с `rejected` показываются пользователю и откатываются локально.
- **WEB-S3\*must.** Вход и регистрация (сделано); добавить OAuth Google, восстановление пароля, 2FA, обновление access-токена в Web Worker без разлогина.

- **WEB-S6\*must.** Индикатор состояния: «синхронизировано / N изменений в очереди / офлайн / ошибка»; ручной повтор.
- **WEB-S7\*must.** Миграции схемы Dexie версионированы; обновление приложения не теряет очередь операций.
- **WEB-S8\*must.** Service Worker: стратегия обновления «новая версия готова — обновить», без принудительной перезагрузки посреди ввода.

## 4. Android-приложение: production-объём

Главное правило: доменная логика берётся только из `shared` (Android-цель KMP), Android-код не повторяет парсеры, повторы и слияние.

### 4.1. Архитектура

- Gradle-модули: `:app`, `:feature:tasks`, `:feature:lists`, `:feature:search`, `:feature:task-detail`, `:feature:settings`, `:feature:auth`, `:feature:billing`, `:feature:widgets`, `:core:data`, `:core:database`, `:core:network`, `:core:sync`, `:core:notifications`, `:core:designsystem`, `:core:testing`, `:shared`.
- Слои: Compose UI → ViewModel (StateFlow, UDF) → репозитории → Room + очередь операций → sync-движок. UI читает только Room.
- DI — Hilt; сеть — Ktor Client + kotlinx.serialization; навигация — Navigation Compose с типобезопасными маршрутами.
- Минимум Android 8.0 (API 26), target и compile — актуальный API Google Play на момент релиза.

### 4.2. Данные и синхронизация

| ID | Требование | Приор. |

| AND-S2\* | Изменение и запись операции в очередь — одна транзакция Room | must |

## 5. Качество, CI, наблюдаемость, релизы

Каждый критерий приёмки проверяется через публичный интерфейс продукта (API, UI), а не через внутренние классы.

### 5.1. Требования к тестам

- **QA-1.** Критерии приёмки — сквозные тесты: API-уровень для сервера, Playwright для веба, Compose UI-тесты + Maestro для Android.
- **QA-2.** Каждая найденная ошибка закрывается регрессионным тестом.
- **QA-3.** Эквивалентность языка запросов на реальном PostgreSQL: один запрос → одинаковый набор id на сервере, в Dexie и в Room; снапшот SQL.
- **QA-4.** Матрица доступа (SEC-4) и конфликты — интеграционными тестами.
- **QA-5.** Межклиентский E2E: задача офлайн на Android-эмуляторе → видна в вебе ≤ 2 с (ночные, не PR).
- **QA-6.** Нагрузочный тест (k6): 10 000 WebSocket, 500 sync-пакетов/с, p95 ≤ 2 с.
- **QA-7.** `STATUS.md` формируется автоматически из CI.

### 5.2. CI/CD

| Этап | Web | Android |
| --- | --- | --- |
| **Проверки PR** | ESLint, typecheck, Vitest, Playwright (Chromium, WebKit), axe, лимит бандла | ktlint/detekt, юнит-тесты, Roborazzi-скриншоты |
| **Ночные** | Полный Playwright на 4 браузерах, межклиентский E2E (QA-5) | Maestro на API 26/30/34/35, Macrobenchmark старта/прокрутки, Compose UI-тесты на эмуляторе |
| **Доставка** | staging авто → prod после ручного подтверждения, CDN с атомарной сменой, откат ≤ 5 мин | Внутренний трек → закрытое тестирование → поэтапный выпуск 5 % → 20 % → 100 % |

### 5.3. Наблюдаемость клиентов

- Sentry (веб и Android), Crashlytics; `trace_id` OpenTelemetry от клиента до БД.
- Метрики: время синхронизации, размер очереди, отклонённые операции, опоздание напоминаний, Web Vitals.
- Фича-флаги (SEC-7, `/v1/features`): удалённое включение/отключение по тарифу, проценту, версии клиента.

## 7. План работ

Публичный релиз веба и Android — через **28 недель** от слияния ветки исправлений (22 нед. + 6 нед. буфер), при команде 7 человек (2 бэкенд, 2 веб, 2 Android, 1 дизайнер) + QA и продакт на частичной.
