# Taskly (my-rtm) — Спецификация ядра

Источник правды для автономной команды (architect → coder → integrator). Полные оригинальные
документы — в `docs/original/SPEC_taskly.md` (функциональная спецификация) и
`docs/original/ARCH_taskly.md` (архитектура решения). Этот документ фиксирует скоуп данного
прогона и критерии приёмки.

## Goal

Построить ядро кроссплатформенного менеджера задач в духе Remember The Milk: одна строка
быстрого ввода (Smart Add) разбирается на свойства задачи, данные живут локально на клиенте
(local-first), синхронизируются с сервером идемпотентными операциями, клиент работает офлайн.
Прогон закрывает: общий доменный модуль (KMP), бэкенд (Ktor + PostgreSQL + Redis) и веб-SPA с
офлайн-очередью. Android в этом прогоне — только shared-модуль и JVM-юнит-тесты (без SDK, без UI).

## Users

- Занятые профессионалы и сторонники GTD — личное использование.
- Основной сценарий: «выгрузить задачу из головы за секунды» через Smart Add; не забыть о сроках;
  видеть задачи на любом устройстве, включая офлайн.

## Features

- **F-1 Модель данных.** User, List (системный «Входящие» + пользовательские), Task (name,
  list_id, priority 1/2/3/none, due_date + due_has_time, start_date, estimate_min, repeat_rule
  (RRULE RFC 5545) + режим every/after, url, completed_at, postponed_count, version, мягкое
  удаление deleted_at), Tag (уникален в аккаунте), Note (markdown), Reminder (поля — на будущее),
  SavedSearch (список с is_smart=true и query). UUIDv7, created_at/updated_at/deleted_at/version.
- **F-2 Smart Add.** Парсер одной строки: `^` срок, `~` дата начала, `!` приоритет, `#` список или
  тег (список приоритетнее), `*` повтор (`*каждую неделю`, `*after 2 weeks`), `@` локация, `=`
  оценка (`=30 мин`), `+` контакт (парсится, передача — вне прогона), `//` заметка. Даты RU и EN:
  «через 3 дня», «сегодня/завтра/послезавтра», дни недели, 12/24-часовое время. Парсер возвращает
  структурированный результат + позиции токенов для подсветки. Распознавание детерминированное,
  rule-based (без ML).
- **F-3 Язык запросов.** Лексер/парсер → AST: `AND`/`OR`/`NOT`, скобки, поля `list:`, `tag:`,
  `priority:`, `due:`, `dueBefore:`, `dueWithin:"1 week"`, `completed:`, `isRepeating:`,
  `hasSubtasks:`, `location:`, `isShared:`, `addedWithin:`, `postponed:>2`, `timeEstimate:"<1 hour"`.
  AST исполняется как предикат над локальной базой (клиент) и транслируется в SQL (сервер, jOOQ).
- **F-4 Повторы.** RRULE + режимы every (от плановой даты) / after (от даты выполнения). При
  завершении повторяющейся задачи следующий экземпляр создаёт сервер (единственная точка
  создания), с тегами и заметками родителя; учёт часового пояса и DST.
- **F-5 Синхронизация.** Идемпотентные операции с `op_id` (create/update/delete/complete/
  uncomplete/move/tag_add/tag_remove, только изменённые поля), серверный `change_log` с
  монотонным `seq` по scope (личный scope + scope общих списков в будущем), курсорная дельта-
  синхронизация, LWW по полям с `field_versions` и правилами из ARCH (завершение побеждает
  переименование; удаление побеждает правку; дубль завершения повтора не создаёт второй
  экземпляр). Сигнал «есть изменения» — WebSocket (выдача дельт клиент делает сам по курсору).
  Идемпотентность через `processed_ops`. Пакет до 500 операций.
- **F-6 Веб-SPA.** React 19 + TypeScript + Vite, Zustand (UI), Dexie/IndexedDB (данные), Workbox
  (PWA): список задач (виртуализация >200), поле Smart Add с подсветкой токенов и
  автодополнением, чекбоксы, массовые действия (базово), системные представления («Сегодня»,
  «Просрочено» и т.п.), поиск с сохранением умного списка, локальная очередь операций в Web
  Worker, реконнект-синк, офлайн-баннер. Локальный полнотекстовый индекс — MiniSearch в Worker.
- **F-7 Android (каркас).** Gradle-модули `:app`, `:feature:*`, `:core:*`, `:shared` по ARCH;
  Room-схема по модели; репозитории; синк-движок; юнит-тесты на JVM. UI-экраны, виджеты, FCM,
  напоминания — вне прогона.
- **F-8 REST API.** `/health`; `/v1/tasks` (GET с фильтром `q=` тем же языком запросов, POST со
  `smart_add=true`), PATCH/DELETE/`complete`; `/v1/lists`, `/v1/tags`; базовые лимиты rate limit
  в Redis (token bucket). Аутентификация: email+пароль (Argon2id) + JWT (access 15 мин + refresh);
  Google OAuth и 2FA — вне прогона.

## Non-goals (вне этого прогона)

- Android UI, виджеты, FCM, геонапоминания, точные будильники.
- Напоминания (push/email/ежедневная сводка), Web Push.
- Общие списки, контакты, передача задач, лента активности (scope готов, фичи нет).
- Подзадачи (parent_id в модели допустим, реализация — нет).
- Вложения, интеграции (email-to-task, Zapier/IFTTT, Drive/Dropbox, iCal, вебхуки), скрипты
  автоматизации (GraalJS), биллинг/тарифы.
- OpenSearch: полнотекстовый поиск в этом прогоне — Postgres (ILIKE/tsvector/trigram) как fallback
  из ADR-5; OpenSearch-индекс отложен.
- Онбординг, импорт/экспорт (CSV/PDF/iCal), корзина с автоочисткой 30 дней (мягкое удаление — да,
  фоновая очистка — нет).

## Assumptions

- Стек зафиксирован архитектурой: Kotlin 2.x (KMP: JVM + JS targets), Ktor 3, jOOQ, Flyway,
  PostgreSQL 16, Redis 7, React 19/TS/Vite/Zustand/Dexie/Workbox. Сервер — модульный монолит в
  ролях api/worker/scheduler (в прогоне работает роль api; worker/scheduler — каркас).
- Окружение на хосте: JDK 21, PostgreSQL 16 (localhost:5432), Redis (localhost:6379) установлены
  и запущены. Интеграционные тесты используют локальные PG/Redis (без Testcontainers/Docker).
- Shared-модуль собирается на JVM и Kotlin/JS (ES-модуль c TS-декларациями); поведение на обеих
  целях идентично и проверяется общим корпусом тестов на обеих целях.
- Аутентификация: пароль + JWT. OAuth, 2FA, refresh-ротация с отзывом — после ядра.
- Часовой пояс по умолчанию для тестов повторов — Europe/Moscow (фикс.), DST-кейс в корпусе.
- WEB UI не обязан повторять трёхпанельный UX и горячие клавиши из спеки — только базовые
  сценарии (список, добавление, завершение, редактирование, поиск, офлайн).
- Redis в прогоне используется для WebSocket-фанаута (pub/sub) и rate limit.

## Acceptance criteria

Каждый AC проверяется командой. В `docs/STATUS.md` фиксируются команда и хвост вывода.

- **AC-1** `./gradlew :shared:allTests` — корпус общего модуля зелёный на JVM и JS.
- **AC-2** Корпус Smart Add ≥ 300 строк ввода (RU+EN, включая относительные даты, `*after`,
  комбинации токенов); 100 % кейсов проходят; результат парсинга идентичен на JVM и JS
  (сравнение структур в тесте).
- **AC-3** `./gradlew :server:integrationTest` — зелёный на локальных PG/Redis (создание тестовой
  БД в прогоне); `curl -s localhost:8080/health` → 200 после `./gradlew :server:run`.
- **AC-4** Идемпотентность: повторная отправка пакета с тем же `op_id` не создаёт дубликат
  (тест + ручная проверка curl).
- **AC-5** Повтор: `complete` задачи с `*каждую неделю` (every) создаёт следующий экземпляр с
  верной датой; режим `after` сдвигает от даты выполнения; DST-кейс (Europe/Moscow) в корпусе
  зелёный.
- **AC-6** Умный список с ≥ 3 операторами (например `list:Работа AND (priority:1 OR
  dueBefore:"3 days")`) возвращает одинаковый набор задач на клиенте (AST-предикат) и в API
  (SQL) — тест эквивалентности в общем корпусе.
- **AC-7** Веб: `npm run build` без ошибок; `npm test` (Vitest) зелёный, включая тест
  «создание задачи при недоступном сервере → после восстановления операция уходит и задача
  видна в API» (офлайн-очередь).
- **AC-8** E2E-смоук по сценарию: POST задачи через API со `smart_add=true` (строка с `^` и `#`)
  → задача в правильном списке со сроком; GET `/v1/tasks?q=...` возвращает её; `git status`
  чистый; `docs/STATUS.md` заполнен таблицей AC с PASS/FAIL и командами.
