# Архитектура решения: Taskly (Web + Android)

Oct 17, 2026 · @Ro

## 1. Обзор и принципы

Taskly — local-first система: клиенты (веб и Android) хранят полную рабочую копию данных пользователя, все действия выполняются локально, а сервер служит источником истины и шиной синхронизации. Бэкенд — модульный монолит на Kotlin/Ktor с выделенными воркерами, а не россыпь микросервисов: при команде из 2 бэкенд-разработчиков это дешевле в поддержке и легко режется позже.

**Принципы**

1. **Local-first.** UI никогда не ждёт сеть; операция пишется в локальную БД и очередь, затем уходит на сервер.
2. **Одна доменная логика.** Парсер Smart Add, язык запросов умных списков и вычисление повторов живут в одном модуле Kotlin Multiplatform и собираются для сервера, Android и веба — поведение совпадает побайтно.
3. **Операции, а не состояния.** Синхронизация передаёт идемпотентные операции с `op_id`, сервер упорядочивает их и раздаёт дельты.
4. **Модульный монолит.** Чёткие границы модулей внутри одного деплоя; взаимодействие между модулями только через интерфейсы и доменные события.
5. **Асинхронно всё, что может подождать.** Уведомления, индексация, вебхуки, письма — через очередь и воркеры.
6. **Наблюдаемость с первого дня.** Трассировка запроса от клиента до БД, метрики SLO, алерты.

**Ключевые качества и целевые значения** (из спецификации)

| Атрибут | Цель |
| --- | --- |
| Задержка синхронизации между устройствами | ≤ 2 с, p95 |
| Доступность API | 99.9 % в месяц |
| Доставка напоминаний | ≤ 60 с, p99 |
| Масштаб без смены архитектуры | 1 млн пользователей, 200 млн задач |
| RPO / RTO | 15 мин / 1 ч |

## 2. Контейнеры системы

Система состоит из двух клиентов, одного серверного приложения в трёх ролях и четырёх хранилищ; с внешними сервисами работает только сервер.

&#91;embedded content: контейнеры · 2 клиента, 3 роли сервера, 4 хранилища, 4 внешних сервиса\]

Клиенты обращаются только к роли `api`; `worker` и `scheduler` не имеют входящего трафика и получают работу через БД и очереди.

| Контейнер | Ответственность | Протоколы |
| --- | --- | --- |
| Веб (PWA) | UI, локальная копия данных, очередь операций, Web Push | HTTPS, WSS |
| Android | UI, локальная копия, фоновая синхронизация, локальные напоминания, виджеты | HTTPS, WSS, FCM |
| `api` | REST API, аутентификация, приём и раздача операций синхронизации, WebSocket-фанаут | HTTPS, WSS |
| `worker` | Обработка outbox: индексация, вебхуки, письма, push, скрипты, экспорт | Redis Streams |
| `scheduler` | Поиск наступивших напоминаний, сводки, периодические задачи (очистка корзины, партиции) | SQL, Redis Streams |

## 3. Клиенты

Оба клиента устроены одинаково: UI → состояние/ViewModel → репозиторий → локальная БД + очередь операций → sync-движок. UI читает только из локальной БД (реактивные запросы), поэтому изменения с сервера появляются на экране без отдельной логики.

### 3.1. Общий модуль `shared` (Kotlin Multiplatform)

| Пакет | Содержимое | Цели сборки |
| --- | --- | --- |
| `domain.model` | Task, List, Tag, Note, Location, Reminder, правила валидации | JVM, Android, JS |
| `smartadd` | Токенизатор и парсер Smart Add, словари дат RU/EN, подсветка токенов | JVM, Android, JS |
| `query` | Лексер, парсер и интерпретатор языка запросов умных списков → AST → предикат над задачей и SQL для сервера | JVM, Android, JS |
| `recurrence` | RRULE, режимы `every`/`after`, расчёт следующей даты с учётом часового пояса | JVM, Android, JS |
| `sync.protocol` | DTO операций и дельт, сериализация (kotlinx.serialization), правила слияния полей | JVM, Android, JS |

Веб получает модуль как ES-модуль с TypeScript-декларациями (Kotlin/JS IR). Общий корпус тестов (≥ 500 строк Smart Add, ≥ 200 запросов) прогоняется на всех трёх целях в CI.

### 3.2. Веб-приложение

- **Стек:** React 19, TypeScript, Vite, React Router, Zustand (UI-состояние), Dexie поверх IndexedDB (данные), Workbox (PWA, офлайн-кэш оболочки).
- **Слои:** `app` (маршруты, оболочка) → `features/*` (tasks, lists, search, settings, sharing) → `entities/*` (репозитории над Dexie) → `sync` (движок, работает в Web Worker, чтобы не блокировать UI) → `shared` (KMP-модуль, UI-кит).
- **Реактивность:** `useLiveQuery` Dexie подписывает компоненты на выборки; виртуализированный список (TanStack Virtual) для списков > 200 задач.
- **Несколько вкладок:** одна вкладка-лидер держит WebSocket и пишет в БД (BroadcastChannel + Web Locks), остальные получают изменения через IndexedDB.
- **Push:** Web Push через Service Worker, подписка VAPID.

### 3.3. Android-приложение

- **Стек:** Kotlin, Jetpack Compose, Material 3, Navigation Compose, Hilt, Room, Kotlin Flow, WorkManager, Glance (виджеты), FCM, Geofencing API.
- **Модули Gradle:** `:app`, `:feature:tasks`, `:feature:lists`, `:feature:search`, `:feature:settings`, `:feature:widgets`, `:core:data` (Room, репозитории), `:core:sync`, `:core:notifications`, `:core:designsystem`, `:shared`.
- **Синхронизация в фоне:** WebSocket, пока приложение на экране; в фоне — FCM data-сообщение «есть изменения» → `OneTimeWorkRequest` на дельту; периодическая страховка раз в 6 ч.
- **Напоминания:** планируются локально через `AlarmManager.setExactAndAllowWhileIdle` на ближайшие 7 дней, перепланирование после каждой синхронизации и после `BOOT_COMPLETED`. Сервер дублирует push только для устройств без точных будильников.
- **Виджеты:** Glance читает Room напрямую; обновление по событию изменения данных.

## 4. Бэкенд

Один код (`taskly-server`) разворачивается в трёх ролях: `api` (HTTP + WebSocket), `worker` (очереди) и `scheduler` (напоминания и периодические задачи). Роль задаётся переменной окружения; модули внутри общие.

### 4.1. Модули

| Модуль | Ответственность | Роль |
| --- | --- | --- |
| `identity` | Регистрация, вход, OAuth Google, 2FA, сессии, токены API | api |
| `tasks` | CRUD задач, списков, тегов, заметок, локаций; повторы; массовые операции | api |
| `sync` | Приём пакетов операций, упорядочивание, журнал изменений, выдача дельт, WebSocket-фанаут | api |
| `search` | Умные списки (SQL из AST), полнотекстовый поиск через OpenSearch | api, worker |
| `sharing` | Контакты, общие списки, права, передача задач, лента активности | api |
| `notifications` | Расчёт и отправка напоминаний, ежедневная сводка, push/email/web push | scheduler, worker |
| `integrations` | Email-to-task, вебхуки, Zapier/IFTTT, Drive/Dropbox, iCal-фид | api, worker |
| `billing` | Stripe, Google Play Billing (RTDN), статус Pro, фича-флаги тарифа | api, worker |
| `automation` | Пользовательские скрипты в песочнице (GraalJS, лимиты CPU/памяти/времени) | worker |

Межмодульные события (`TaskCompleted`, `ListShared` и т. п.) публикуются через transactional outbox в той же транзакции, что и изменение данных, и разносятся воркером в Redis Streams.

### 4.2. Хранилища

| Хранилище | Данные | Примечания |
| --- | --- | --- |
| PostgreSQL 16 | Все доменные данные, журнал изменений, outbox | Основной + 2 реплики; партиционирование `change_log` по месяцам |
| Redis 7 | Сессии, rate limiting, presence WebSocket, Redis Streams для очередей | Кластер из 3 узлов |
| OpenSearch | Индекс задач и заметок для полнотекстового поиска | Наполняется асинхронно из outbox; источник истины — PostgreSQL |
| S3-совместимое | Загруженные вложения, экспорты, бэкапы | Доступ по подписанным URL, срок 15 мин |

### 4.3. Ключевые таблицы

| Таблица | Ключевые столбцы | Индексы |
| --- | --- | --- |
| `users` | id, email, tz, locale, plan, settings jsonb | email unique |
| `lists` | id, owner\_id, name, is\_smart, query, archived, sort, version | (owner\_id) |
| `tasks` | id, owner\_id, list\_id, parent\_id, name, priority, due\_at, due\_has\_time, start\_at, estimate\_min, rrule, repeat\_mode, location\_id, completed\_at, postponed, assignee\_id, deleted\_at, version, field\_versions jsonb | (list\_id, completed\_at, due\_at), (owner\_id, updated\_seq), частичный по `completed_at IS NULL` |
| `tags`, `task_tags` | id, owner\_id, name, color / task\_id, tag\_id | (owner\_id, lower(name)) unique |
| `notes`, `attachments`, `locations`, `reminders` | id, task\_id, … | (task\_id) |
| `list_members` | list\_id, user\_id, permission, status | (user\_id) |
| `change_log` | seq bigserial, scope\_id, entity, entity\_id, op, payload jsonb, actor, ts | (scope\_id, seq) |
| `processed_ops` | op\_id, user\_id, result, ts | op\_id PK, TTL 30 дней |
| `outbox` | id, type, payload, created\_at, sent\_at | частичный по `sent_at IS NULL` |

`scope_id` — пространство синхронизации: личное пространство пользователя или общий список. Клиент подписан на свой scope и scope каждого общего списка; курсор хранится по каждому scope отдельно.

Доступ к данным — через jOOQ (типобезопасный SQL, удобно для запросов из AST умных списков); миграции — Flyway.

## 5. Протокол синхронизации

Клиент шлёт на сервер идемпотентные операции, сервер упорядочивает их в `change_log` и рассылает остальным устройствам только сигнал «есть изменения»; данные каждый клиент забирает сам по своему курсору.

&#91;embedded content: синхронизация · правка на A доходит до B\]

Шаги 5–7 одинаковы для других устройств того же пользователя и для участников общего списка; на свёрнутом Android шаг 5 идёт через FCM.

### 5.1. Формат операции

```json
{
  "op_id": "0192f7c4-5b1e-7a2c-9e3d-1f2a3b4c5d6e",
  "scope": "user:7f3a…",
  "entity": "task",
  "entity_id": "0192f7c4-…",
  "type": "update",
  "fields": { "due_at": "2026-10-20T17:00:00+03:00", "priority": 1 },
  "base_version": 14,
  "client_ts": "2026-10-17T10:42:11.120Z",
  "device_id": "android-5c1e"
}
```

Типы: `create`, `update` (только изменённые поля), `delete`, `complete`, `uncomplete`, `move`, `tag_add`, `tag_remove`. Идентификаторы — UUIDv7, генерируются на клиенте, поэтому задачу можно создать и сразу править офлайн.

### 5.2. Обработка на сервере

1. Пакет до 500 операций обрабатывается последовательно, каждая — в своей транзакции.
2. `op_id` уже в `processed_ops` → вернуть сохранённый результат (идемпотентность).
3. Проверка прав на scope и валидация общим модулем `domain`.
4. Слияние: для каждого поля сравниваются `field_versions`; если поле изменено на сервере после `base_version`, побеждает последняя запись по серверному порядку.
5. Запись в `tasks`, `change_log` (новый `seq`), `outbox`, `processed_ops` — одной транзакцией.
6. После коммита — публикация `scope, seq` в Redis Pub/Sub, все поды `api` уведомляют свои WebSocket-соединения.

### 5.3. Правила разрешения конфликтов

| Ситуация | Результат |
| --- | --- |
| Разные поля одной задачи изменены на двух устройствах | Оба изменения сохраняются |
| Одно поле изменено дважды | Побеждает позднее по серверному порядку; для названия и заметок проигравшая версия сохраняется в истории и показывается диалог |
| Одно устройство завершило, другое переименовало | Задача завершена и переименована |
| Повторяющаяся задача завершена на двух устройствах офлайн | Следующий экземпляр создаёт только сервер, второе завершение становится недействующим (нет дублей) |
| Правка удалённой задачи | Удаление побеждает, правка применяется к задаче в корзине |
| Участника лишили доступа, а у него есть офлайн-правки | Операции отклоняются с кодом `forbidden`, клиент удаляет локальную копию списка и сообщает пользователю |

### 5.4. Первая синхронизация и долгий офлайн

Новое устройство или курсор старше 90 дней получает снимок: все невыполненные задачи и выполненные за 90 дней, потоково (NDJSON, страницами по 1 000) с курсором на момент начала. Более старые выполненные задачи догружаются по запросу (вкладка «Выполненные», поиск).

## 6. Напоминания, поиск, интеграции

### 6.1. Напоминания

1. При изменении срока, повтора или напоминания задачи модуль `tasks` пересчитывает ближайшее время срабатывания и пишет его в таблицу `reminder_schedule` (task\_id, fire\_at, channel).
2. `scheduler` раз в 15 с выбирает записи с `fire_at <= now() + 30 s` через `SELECT … FOR UPDATE SKIP LOCKED` — несколько экземпляров работают без дублей.
3. Записи уходят в поток `reminders` Redis Streams; воркеры отправляют через FCM, Web Push (VAPID) или SMTP-провайдера.
4. Для Android-устройств с локальными будильниками сервер не шлёт push по умолчанию (флаг устройства `local_alarms=true`), чтобы не было двойных уведомлений.
5. Ежедневная сводка: задание на каждого пользователя в его часовом поясе, группируются по 5-минутным окнам.

Действия из уведомления («Выполнить», «Отложить») отправляются как обычные sync-операции.

### 6.2. Поиск и умные списки

- Запрос умного списка парсится общим модулем `query` в AST. На клиенте AST исполняется как предикат над локальной БД; на сервере — транслируется в SQL (jOOQ) для API и iCal-фида.
- Полнотекстовые условия (свободные слова, `noteContains:`) уходят в OpenSearch, результат пересекается с SQL-фильтром по id.
- Офлайн полнотекстовый поиск на клиентах: FTS5 в Room (Android), MiniSearch-индекс в Web Worker (веб).

### 6.3. Интеграции

| Интеграция | Механизм |
| --- | --- |
| Email-to-task | Входящая почта провайдера → webhook → парсинг темы Smart Add → операция создания |
| Вебхуки, Zapier, IFTTT | Подписки хранятся в БД; события из outbox → воркер → HTTP POST с HMAC-подписью, ретраи с экспоненциальной задержкой до 24 ч |
| Google Drive, Dropbox | OAuth провайдера; в задаче хранится ссылка и метаданные файла, сам файл не копируется |
| iCal-фид | Неугадываемый токен в URL, кэш 15 мин, только задачи со сроком |
| Публичный API | Тот же модуль `tasks`, версия `/v1`, OAuth 2.0 + токены приложений, rate limit в Redis (token bucket) |
| Скрипты автоматизации | GraalJS в отдельном пуле воркеров: 5 с CPU, 64 МБ, без сети кроме API Taskly |

## 7. Безопасность

| Область | Решение |
| --- | --- |
| Аутентификация | Email + пароль (Argon2id), OAuth Google, TOTP 2FA; access-токен JWT 15 мин + refresh-токен 60 дней с ротацией и отзывом |
| Хранение токенов на клиентах | Веб: refresh в httpOnly Secure SameSite=Strict cookie, access в памяти. Android: EncryptedSharedPreferences / Keystore |
| Авторизация | Проверка scope на каждом запросе и каждой sync-операции: владелец или участник списка с нужным правом; тесты на межпользовательский доступ в CI |
| Транспорт | TLS 1.2+, HSTS, certificate pinning не используется (риск блокировки при ротации) |
| Данные в покое | Шифрование дисков БД и S3 (KMS), бэкапы шифруются отдельным ключом |
| Веб | CSP без `unsafe-inline`, Trusted Types, защита от CSRF через SameSite + заголовок |
| Злоупотребления | Rate limiting по IP и пользователю, CAPTCHA после 5 неудачных входов, лимиты на размер пакета операций (500 оп.) |
| Вебхуки и скрипты | HMAC-подпись исходящих вебхуков, запрет обращений к внутренним адресам (SSRF), песочница GraalJS |
| Секреты | Vault / облачный Secret Manager, ротация ключей раз в 90 дней |
| Аудит и приватность | Журнал входов и смены настроек безопасности; экспорт и удаление аккаунта (удаление данных за 30 дней, из бэкапов — по истечении срока хранения) |

Регион размещения данных и требования 152-ФЗ — открытый вопрос; архитектура допускает отдельный региональный кластер, так как данные пользователя не пересекают scope других регионов, кроме общих списков.

## 8. Развёртывание, масштабирование, наблюдаемость, CI/CD

### 8.1. Окружения и инфраструктура

Три окружения — `dev`, `staging`, `prod` — описаны в Terraform и развёрнуты в управляемом Kubernetes в одном облачном регионе с тремя зонами доступности.

| Компонент | Prod-конфигурация на старте | Масштабирование |
| --- | --- | --- |
| `api` | 3 пода × 2 vCPU / 4 ГБ, по одному на зону | HPA по CPU и числу WebSocket-соединений (цель 20 000 на под) |
| `worker` | 2 пода | HPA по длине очередей Redis Streams |
| `scheduler` | 2 пода (конкурентный захват через SKIP LOCKED) | Горизонтально |
| PostgreSQL | Управляемый, 8 vCPU / 32 ГБ, 2 реплики, PITR | Вертикально; при > 50 млн задач — шардирование по `owner_id` (Citus) |
| Redis | Управляемый кластер, 3 узла | Горизонтально |
| OpenSearch | 3 узла | Горизонтально |
| Веб-клиент | Статические файлы в S3 + CDN | — |

Inbound: CDN/WAF → L7-балансировщик (sticky не требуется: WebSocket-фанаут через Redis Pub/Sub, любой под доставляет событие любому клиенту).

### 8.2. Наблюдаемость

- **Трассировка:** OpenTelemetry на сервере и в обоих клиентах; `trace_id` передаётся в заголовке и в sync-операциях.
- **Метрики:** Prometheus + Grafana. SLO-дашборды: задержка синхронизации, доля ошибок API, задержка напоминаний, длина очередей, lag репликации.
- **Логи:** структурированный JSON → Loki; персональные данные (названия задач) не логируются.
- **Ошибки клиентов:** Sentry (веб, Android), Firebase Crashlytics как дубль для Android-vitals.
- **Алерты:** по сжиганию бюджета ошибок SLO (multi-window), дежурство через PagerDuty/Opsgenie.

### 8.3. CI/CD

| Этап | Сервер | Веб | Android |
| --- | --- | --- | --- |
| Проверки на PR | Детект, ktlint, юнит- и интеграционные тесты (Testcontainers), тесты `shared` на JVM/JS | ESLint, тесты Vitest, Playwright по ключевым сценариям | Lint, юнит-тесты, Compose-скриншотные тесты (Roborazzi) |
| Сборка | Docker-образ, подпись (cosign) | Статический бандл | AAB, подпись в Play App Signing |
| Доставка | Argo CD: staging автоматически, prod — canary 10 % → 100 % по метрикам | Деплой в CDN с атомарной сменой версии | Внутренний трек → закрытое тестирование → поэтапный выпуск 5 % → 100 % |
| Миграции БД | Flyway, только обратно совместимые (expand → migrate → contract) | — | — |

Совместимость версий: сервер поддерживает протокол синхронизации двух последних мажорных версий клиента; устаревший Android-клиент получает мягкое, затем жёсткое требование обновиться.

## 9. Архитектурные решения и риски

### 9.1. ADR

| № | Решение | Рассмотренные альтернативы | Почему так |
| --- | --- | --- | --- |
| ADR-1 | Модульный монолит + воркеры | Микросервисы | Команда 2 бэкенд-разработчика; одна транзакция для задачи и outbox; границы модулей позволяют выделить сервис позже |
| ADR-2 | Kotlin/Ktor на сервере | Node.js, Go | Общий KMP-модуль с Android и вебом, без дублирования парсеров и повторов |
| ADR-3 | Local-first, операции + LWW по полям | Серверный рендер состояния; CRDT (Automerge, Yjs) | Данные задач — плоские записи, конкуренция редкая; LWW по полям проще CRDT и закрывает 99 % случаев |
| ADR-4 | Курсор по `change_log` на scope | Version vectors, полная перезагрузка | Монотонный `seq` в PostgreSQL прост и надёжен; scope даёт общие списки без лишних данных |
| ADR-5 | PostgreSQL как единственный источник истины, OpenSearch — производный индекс | Поиск только в PostgreSQL (tsvector) | Морфология RU/EN и ранжирование лучше в OpenSearch; при недоступности — деградация до tsvector |
| ADR-6 | Redis Streams для очередей | Kafka, RabbitMQ | Redis уже нужен; объёмы на старте малы; переход на Kafka — заменой адаптера |
| ADR-7 | Локальные будильники на Android + серверный push как резерв | Только серверный push | Срабатывание офлайн и в Doze; меньше зависимость от FCM |
| ADR-8 | Веб на React + Kotlin/JS только для `shared` | Полностью Kotlin/Compose for Web | Зрелая экосистема и найм; KMP используется там, где даёт выгоду |

### 9.2. Риски

| Риск | Влияние | Митигация |
| --- | --- | --- |
| Размер и скорость Kotlin/JS-бандла `shared` | Медленный первый запуск веба | Ленивый импорт парсера запросов, цель ≤ 150 КБ gzip, замер в CI |
| Ограничения точных будильников Android 14+ | Напоминания приходят с опозданием | Запрос разрешения в онбординге, серверный push как резерв, метрика опозданий |
| Рост `change_log` | Медленная синхронизация, объём БД | Партиции по месяцам, компактация: клиенту с курсором старше 90 дней — полный снимок |
| Конфликты при работе офлайн в общих списках | Потеря правок | LWW по полям + журнал активности; диалог выбора версии для названия и заметок |
| Блокировки Google-сервисов (FCM) в отдельных регионах | Нет push | WebSocket при открытом приложении, локальные будильники, периодическая синхронизация WorkManager |
| Неточный разбор дат Smart Add на русском | Неверные сроки, недоверие к продукту | Корпус тестов из реальных фраз беты, подсветка распознанного до сохранения |
